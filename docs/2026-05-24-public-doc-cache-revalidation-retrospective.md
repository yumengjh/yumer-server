# 2026-05-24 公开文档缓存失效与发布链路复盘（后端视角）

## 1. 复盘目的

这份复盘文档从后端视角总结本轮公开文档缓存优化中的三个核心问题：

1. 内容接口如何区分公开阅读与调试兼容场景
2. 发布后如何让前端缓存尽快失效
3. 在不牺牲稳定性的前提下，如何让页面体验尽量接近 SSG

---

## 2. 这轮后端到底解决了什么

### 2.1 解决了 `mode=html` 与 `mode=all` 语义不清的问题

过去：

- `mode=html` 与 `mode=all` 返回非常接近
- 已渲染块通常保留 `html + payload`
- 对公开页来说并不够轻

现在：

- `mode=html`：已渲染块只保留 `html`
- `mode=all`：保留 `html + payload`

因此公开页默认模式终于真正轻量化了。

### 2.2 解决了“发布后只能等时间过期”的问题

过去：

- 页面虽然可以缓存
- 但发布后是否立刻刷新，更多依赖时间 revalidate

现在：

- 后端在 publish 成功后，主动通知前端清掉详情页缓存
- 页面在下次访问时即可重新生成新内容

### 2.3 保留了实时调试通道

这轮设计并没有把缓存做成黑盒：

- `/latest` 仍然是实时读
- 失效通知失败不会让调试无路可走
- 渲染诊断头能帮助开发者判断当前页面来源

---

## 3. 关键设计取舍

### 3.1 为什么把主动失效放在 publish 后，而不是 publish 前

如果放在 publish 前，可能出现：

- 缓存先被打掉
- 但发布事务随后失败

这会让外部行为不一致。

放在 publish 成功后更合理：

- 先保证业务事实成立
- 再尽快刷新缓存
- 更符合用户认知

### 3.2 为什么失效失败不让 publish 失败

因为 publish 和 revalidate 属于主动作与附动作：

- publish 失败：内容事实未成立
- revalidate 失败：内容事实已成立，但缓存刷新未完成

两者语义不同，不能混在一起。

### 3.3 为什么后端自己算 slug

这样做的好处：

- 不需要前端额外传 slug
- 不需要数据库维护另一套 slug 映射
- 只要 `docId -> slug` 编码规则稳定，后端就能独立完成失效通知

---

## 4. 使用说明（后端开发/运维）

### 4.1 开启主动失效

配置：

```env
PUBLIC_SITE_REVALIDATE_URL=http://your-frontend-host/api/revalidate-doc
PUBLIC_SITE_REVALIDATE_SECRET=your-secret
```

### 4.2 关闭主动失效

如果不配置这两个变量，后端会自动跳过主动失效逻辑，不影响 publish 主流程。

### 4.3 如何验证是否正常工作

1. 发布一篇 `public` 文档
2. 查看后端日志是否出现失效失败告警
3. 访问普通页 `/blog/:slug`
4. 再访问实时页 `/blog/:slug/latest`
5. 对比两者内容是否一致

---

## 5. 这轮后端工作的真正价值

从后端角度看，这轮工作并不是“多打一个 HTTP 请求”这么简单，而是让系统第一次真正具备了“发布驱动内容分发”的能力：

- 内容不只是存下来了
- 页面不只是能打开了
- 缓存也不再只是被动等待过期

而是形成了一条更完整的链路：

```txt
编辑 -> 发布 -> 发布版本固化 -> 主动通知前端失效 -> 下次公开访问刷新缓存
```

---

## 6. 后续建议

1. 将失效通知提炼成独立的 `PublicSiteCacheService`
2. 对失败告警增加统计、监控和必要的重试策略
3. 当列表页也进入缓存体系后，在 publish 时同时失效 `/blog`
4. 持续把“编辑态逻辑”和“公开阅读逻辑”分层，而不是在单一路径中叠加更多兼容逻辑

---

## 7. 总结

这轮后端改造，实质上是让“文档发布”第一次真正带上了“内容分发”的语义：

- 内容不只是发布到了数据库
- 页面不只是可以从接口读出来
- 缓存也不再只是被动等待时间过期

而是开始形成一套更完整的公开阅读链路：

```txt
发布成功 -> 主动通知前端失效 -> 默认公开页继续接近静态站体验 -> /latest 保留实时验证入口
```

它还不是最终形态，但已经把系统推进到了“接近静态站体验的动态内容平台”这一层。
